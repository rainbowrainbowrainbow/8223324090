# My Day park edition pilot

Use a local or expressly approved pilot environment. Recruit 3–5 staff; include a user who works chiefly on a phone and one who uses the keyboard. Use synthetic tasks, a synthetic payroll period and test accounts. One observer records the result against each scenario.

| Scenario | Action and expected result |
| --- | --- |
| Usual day | Create a work task and a personal task. A second permitted team member can see the work task through the usual task surface but cannot see the personal task. Existing private fixtures keep their original owner/observer behavior. |
| Find tasks | Locate a dated task, a waiting task, a task without a date, and a task in a later month. Switch Today / Overdue / Future. Load another page and confirm the label and absence of duplicates. |
| Details and report | Open the task by title; check description, checklist and edit, then return to the list. Complete a report-required task and verify the report is required before completion. Restore from the toast and then from History. |
| Mobile and keyboard | Repeat at phone width. Tab through the profile and period controls, use Space or Enter, and Escape to dismiss the actions panel. Review focus after loading more, completing and restoring. |
| Slow or lost connection | Disconnect while loading and during creation. Read the error, reconnect, and retry. Confirm a single created task for a single submission. |
| Results and salary | Read the periods and sources in Results. Confirm the synthetic work task counts and personal tasks do not. Compare the salary summary and reopened breakdown with the same fixture, including partial payments and reversals. |
| Hidden modules | Check that the four old links go to the Soon message. If given a fixture with a pre-existing timer, stop it using the recovery control and confirm it is no longer active. |

For each scenario record: device and browser, role, time to complete, where assistance was needed, severity of any problem, and expected vs observed behavior. Do not include actual payroll amounts or employee identifiers in shared evidence. Record the pilot as pending until participants have completed it.

Before a future release: verify fresh remote and live refs and check parallel release markers; verify exact-SHA CI and the same-version guard; inspect active timer counts read-only and agree on recovery or ask active users to stop their own timers. Request one Yellow block for the intended manual release scope. If a change to authorization or payroll rules is proposed, quote the exact before and after contract and obtain separate Red approval.
