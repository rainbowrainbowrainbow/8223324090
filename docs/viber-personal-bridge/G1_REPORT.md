# G1 — первинна перевірка Viber Desktop

> **Поточний напрям:** структурований локальний DB reader за [GITHUB_REUSE_PLAN.md](GITHUB_REUSE_PLAN.md). Висновки «наступний OCR» нижче — історія попередніх кроків, а не поточний план. G1 exact recipient та new-contact gates залишаються непідтвердженими.

Дата: 2026-09-11. **Статус: PARTIAL / G1 не пройдено.** Production impact: no.

Користувач дозволив перевірити запущений Viber на своєму ПК. Це дозволило огляд поточної сесії, але не встановило, що акаунт є окремим тестовим A. Тестові співрозмовники B/C/D не визначені. Проведено preflight і читання accessibility-структури через штатний інструмент комп’ютерного керування. Код кандидатів не запускався, залежності не встановлювалися, повідомлення не надсилалися, CRM не змінювалася.

## Перевірено запуском інструмента спостереження

1. Читання accessibility tree запущеного Viber успішне. Початковий зріз містив 69 рядків. Пізніші зрізи містили 63 та 66: дерево змінюється; індекс вузла не є постійною identity.
2. У списку було 11 вузлів чатів із тим самим `delegateLoader`. У цьому зрізі вони не мали доступних назв/унікальних дочірніх полів. Це підтверджує недостатність саме цього представлення для адресації; не доводить відсутності даних у всіх UIA patterns чи інших backend.
3. Видимі структурні елементи `ProfileButton`, пошук, `InfoButton`, `FeedDelegate`, `QQuickTextEdit` і `SendToolbarButton`. У першому зрізі були дочірні `TextEditItem`, у наступному вони зникли. Наявність класу текстового елемента не доводить отримання його тексту, напряму, message ID чи повної історії.
4. У повернутому дереві не знайдено буквальних полів `account_id`, `chat_id`, `peer_id`, `message_id`. Це вузька перевірка назв полів, а не вичерпне дослідження identity.
5. Спроба відкрити профіль за актуальним accessibility index повернула `coordinate input geometry is unavailable`. Після повторного визначення вікна, активації та свіжого зрізу виконано одну повторну спробу — та сама помилка. Успішне відкриття профілю не підтверджено; точний ефект невдалих викликів не встановлено. Подальші кліки припинено.

Помилка геометрії належить поточному інструменту керування. Вона **не доводить**, що прямий reviewed UIA observer або всі способи навігації Viber непридатні. Потрібен окремий контрольований дослід, а не висновок про універсальну несумісність Viber 26.3.2.

Повні UI dumps залишалися лише в оперативному контексті інструмента. До звіту винесено структуру й агрегати; номери, імена контактів, текст листування, QR, токени, session DB та screenshots не зберігалися в репозиторій.

## Повторний огляд після звернення користувача

Того ж дня керування відновлено без перезапуску Viber: отримано screenshot-backed state (1088×912 — розмір знімка вікна, не всього дисплея), після чого координатний клік відкрив профіль. Після закриття меню перевірено також клік за свіжим UIA index: він успішно відкрив профіль. Отже, попередня помилка геометрії усунута отриманням знімка перед дією; вона не є поточним блокером навігації. Внутрішню причину в helper не досліджено. Попередня зупинка після text-only snapshots була передчасною.

Візуально підтверджено номер власного акаунта в меню профілю та номер незбереженого контакту в банері вже відкритого чату. Конкретні значення не переносяться у звіт. У відповідних accessibility tree/document_text шаблон номера не знайдено. Це розрізняє **видимі людині дані** та **машинозчитувані поля**. OCR/visual extraction можуть бути гіпотезою наступного досліду, але їх точність і стабільність тут не перевірено.

Наявний історичний чат із незбереженим контактом не є тестом live discovery нового звернення D. Імена чатів видно на зображенні, але їх відповідність конкретним `delegateLoader` не доведено. Успішне відкриття меню також не замінює 30 відкриттів B/C. Меню профілю після огляду закрито; текст не вводився, Send не викликався. Знімки використовувалися в інструменті огляду, у файли репозиторію не зберігалися.

## Висновок і наступна дія

### Додатковий runtime-сеанс: адресат, layout і перекриття

Після наступного дозволу користувача продовжено навігацію без введення тексту. Спостерігали два наявні особисті чати: початковий незбережений контакт та один збережений контакт без видимого лічильника непрочитаних. Це не synthetic B/C; вони не зараховуються до 30 контрольованих відкриттів. Відкриття чату потенційно може позначати повідомлення прочитаними; перевірка серверних read receipts не проводилася.

| Перевірка | Фактичне спостереження | Що це доводить / не доводить |
|---|---|---|
| Перекриття іншим вікном | Знімок містив стороннє вікно поверх Viber, тоді як accessibility tree містило Viber controls. Після activate_window отримано видимий Viber | Screenshot та UIA не можна вважати узгодженими лише через window handle |
| Панель інформації | Клік назви початкового чату закрив панель, ширина message viewport змінилася; номер у банері залишився видимим | Координати й перенесення рядків залежать від layout |
| Максимізація | Знімок 1707×912; номер у банері видно, у tree/document_text шаблон номера не знайдено | Збільшення вікна не розв’язало текстове зчитування в поточному API |
| Збережений контакт | Номер видимий під назвою після відкриття. В іншому кадрі там статус присутності; після кліку підпису номер знову видно | Є потенційне візуальне джерело exact phone, але механізм появи/час життя не встановлено |
| Панель збереженого контакту | Видно назву, але номер не отримано з accessibility. У цьому результаті доступні лише tree і focused_element | Відсутній document_text не є порожнім provider field; дані не повернуті інструментом |
| Повторний клік підпису | Номер лишився видимим; у жодному повернутому текстовому accessibility field шаблон номера не знайдено | Не доводить toggle, OCR-точність або стабільність після restart |
| Повернення | Повернуто початковий чат і віконний режим; фінальний знімок 1088×811 | Не стверджуємо відновлення точного scroll position або початкової висоти |
| Анімація / overlays | Одразу після restore кадр містив накладання перехідних станів; наступний кадр стабільніший, але зверху є сторонній tooltip | Один кадр після успішного кліку недостатній для visual identity proof |

Числа в розмірах — метадані знімків, не доведений physical resolution/DPI. Перевірка номера використовувала шаблон `+` із цифрами/роздільниками; вона не є повним аналізом усіх можливих форматів телефонів. Конкретні номери, назви й листування до звіту не перенесено. Send, дзвінки, реакції, зміни контактів, restart, інсталяції не виконувалися.

### Конкретний наступний дослід зчитування

Поточний Computer Use API повертає дерево й знімок, але не надає довільного доступу до UIA TextPattern/ValuePattern/LegacyIAccessible. Тому цей сеанс не може виключити, що інший observer отримає номер без OCR. Повторення тих самих кліків такого доказу не додасть.

1. На synthetic A/B/C/D перевірити raw UIA Name/AutomationId/ControlType та підтримувані TextPattern/ValuePattern/LegacyIAccessible для заголовка й номера. Не обходити все листування; записувати лише наявність джерела та synthetic alias. Це окремий reviewed observer, поки не реалізований і не запущений.
2. Якщо поля недоступні, оцінити локальний OCR лише області заголовка/профілю. Не використовувати текст message body як джерело адресата. Номер із банера незбереженого контакту — додаткове джерело, яке не працює універсально для збережених контактів. Немає підстав уже зараз виставляти capability verified_recipient=true.
3. Перед зчитуванням підтвердити потрібне вікно, відсутність перекриття області identity, завершення переходу та відповідність поточному відкритому чату. Два узгоджені кадри зменшують ризик анімації, але не доводять правильність OCR. Відсутній/обрізаний/неоднозначний номер означає abort. Після будь-якої навігації попередня перевірка недійсна.
4. Порівнювати з наперед заданим synthetic expected peer; phone normalization не має здогадуватися про код країни. Виконати 30 почергових відкриттів B/C, однакові назви, rename, resize, overlay, restart. Окремо D починає нове звернення. Записати false matches, false rejects і недоступність identity. До завершення — жодного Send.

Рекомендація: спочатку raw UIA observer, потім контрольована оцінка OCR за потреби. Візуальне читання людиною/асистентом у цьому сеансі не є реалізацією автономного Windows worker і не підтверджує його точність.

**LIMITED для продовження досліду; G1 не пройдено, remote Send і повний Omni поки не дозволені технічними критеріями.** Позитивний доказ: інструмент читає структуру Viber 26.3.2. Нерозв’язані питання: exact recipient, account identity, новий контакт, occurrence/direction. Працездатність жодного upstream bridge цим дослідом не підтверджено.

Наступний крок: визначити виключно тестові B/C і окремий D та забезпечити тестову сесію A. Навігація профілю вже працює зі screenshot-backed state. Для автоматичних 30 відкриттів потрібен доказовий спосіб звірки номера відкритого адресата: дослідити доступні UIA fields іншим reviewed observer або окремо оцінити помилки visual extraction. Не встановлювати бібліотеки й не запускати upstream під виглядом уже виконаного preflight. Лише після цього виконувати послідовність G1 з [плану](PROTOTYPE_PLAN.md).

Цей звіт — нові runtime-спостереження. [RESEARCH.md](RESEARCH.md) залишається статичним аудитом коду; заяви авторів у ньому не стають runtime-доказами через запуск локального Viber.

## Реалізовано: окремий raw UIA observer

Після прямого дозволу користувача створено й запущено [Observe-Viber.ps1](observer/Observe-Viber.ps1) та [LegacyProbe.cs](observer/LegacyProbe.cs). [Інструкція та обмеження](observer/README.md). Попередні слова «observer не реалізований» описують стан до цього кроку.

Без нових залежностей: Windows PowerShell 5.1, системні .NET UIA assemblies, невеликий локальний COM helper. Немає коду кліків, введення тексту, активації вікна, мережі або доступу до Viber DB. RawViewWalker обмежено depth/node budget; відомі message/chat-list/composer branches відсікаються. Значення читаються лише в leaf-вузлах евристичної Header/Profile області й перетворюються на ознаки наявності без самих текстів.

Виявлено, що .NET AutomationProperty.LookupById не реєструє Legacy IDs 30090/30092/30093. Тому реалізовано native COM читання: ElementFromPoint плюс перевірка ProcessId та RuntimeId проти raw UIA вузла; лише після успішного зіставлення читаються Legacy Name/Value. Це перевірка відповідності елемента, а не identity адресата.

Фактичний повторний запуск з доступом до інтерактивного desktop: **53 visited, 14 pruned, 7 eligible nodes, 0 traversal errors, 7 unresolved Legacy probes; status=partial, complete=false**. У семи вузлах Name і ValuePattern порожні, TextPattern unsupported. Legacy статус кожного — point_target_mismatch, тому Legacy Name/Value не прочитані. Причину mismatch не встановлено: перекриття, геометрія або hit-test інший вузол. Немає підстав оголосити всі UIA джерела номера відсутніми.

Збережено лише знеособлений [G1_HEADER_RESULT.json](observer/G1_HEADER_RESULT.json). Початковий запуск у sandbox повернув count=0 доступних main windows, хоча процес працював; після запуску поза sandbox raw UIA читання успішне. G1 залишається неповним; capabilities для Send не вмикалися.

Перевірки: synthetic privacy/classifier self-test — 7/7; C# COM helper — успішна компіляція; live Header огляд — виконано, partial. Окремий live запуск з MaxNodes=20 відвідав рівно 20 вузлів і повернув enumeration_limited=true, complete=false, partial: обмеження не маскується успіхом. Примусове зависання provider та end-to-end timeout ще не тестувалися; supervisor timeout реалізовано в окремому процесі. Загальні CRM тести не запускалися: runtime CRM не змінювався.

Наступна конкретна перевірка: Header і вручну відкритий Profile на неперекритому Viber, щоб розрізнити Legacy mismatch від unsupported. Якщо raw UIA так і не дає exact peer, переходити до контрольованого OCR досліду на synthetic B/C/D, а не оголошувати поточний observer мостом.
