# Готовність розділу «Клієнти» до релізу

Дата: 2026-10-03. Production impact: yes після розгортання.
Це знімок перевірок перед випуском; підсумкові докази CI, deploy та live QA
зберігаються окремо в `output/final-sanity/`.

Статус: локальні зміни КЛ-01–КЛ-05 зібрані в одному ізольованому
worktree. Дозвіл на production-реліз цей звіт не замінює. До випуску
потрібні PostgreSQL-перевірки, CI точного релізного SHA та live-site QA.

База підготовлених змін і підтверджена публічним `/api/version` production-база:
`98ad5e139e8409407f7f04bc9ba9ade45567921d`, версія `0.82.51`,
гілка `codex/eventgenix-production`. Локальний кандидат ще не має нового
коміту. Commit, push, deploy, зміни production-даних і повідомлення не виконувалися.

## Що тепер бачить менеджер

- «Клієнти» — основний список із пошуком, фільтрами й пагінацією.
- «Аналітика» містить RFM і NPS / відгуки.
- «Якість даних» містить уточнення даних дітей і можливі дублікати.
- «Підготовка повідомлень» перевіряє текст і сегмент; доставки немає.
- Кожний допоміжний інструмент має пояснення й повернення до списку.
  Перехід між вкладками зберігає пошук, фільтри, сторінку та завантажені рядки.
  Кнопка повернення відновлює фокус на полі пошуку.
- Старі `tab=list|rfm|nps|children-review|duplicates|bulk` збережені.
  Навігація використовує справжні посилання; нова вкладка працює.
  Наявні параметри адреси, включно з бізнес-контекстом, зберігаються.

## Узгодження окремих робіт

| Робота | Результат злиття | Що ще перевірити на справжній БД / live |
| --- | --- | --- |
| КЛ-01 | API відмовляє доставці; preview не пише журнал. Birthday-фільтр переходить зі списку в підготовку. | Повний розмір сегмента на PostgreSQL; журнал тестового клієнта до/після. |
| КЛ-02 | Список, картка, аналітика й preview використовують поточні бронювання. LTV прибраний. | Скасовані, перенесені, пов’язані та пакетні записи; арифметика, дати й межі бізнесу. |
| КЛ-03 | Спільний відбір актуальних дітей, місяців, сімей і лічильників. | SQL-відбір, очищення/зміна дати, 29 лютого, ручні теги та відсутність масового переобчислення. |
| КЛ-04 | Пакетні відомості Omni поєднані з актуальними метриками й birthday-тегами. | Один/кілька/жодного діалогу, зв’язки кількох лідів, однакові телефони в різних бізнесах, збережений WhatsApp. |
| КЛ-05 | Групування, пояснення, старі вкладки, повернення, фокус, помилки. Merge заблокований. | Спільний маршрут після розгортання; чинні облікові записи й права. |

Під час інтеграції виправлено конкретні розбіжності:

1. Preview читав старий `customers.total_bookings`, а список — актуальні
   бронювання. Preview тепер використовує той самий розрахунок з поточних
   бронювань, включно з бізнесом, видимістю, статусами та пов’язаними записами.
2. Birthday-тег і Omni-посилання не відкривають картку рядка одночасно.
3. Пошук дублікатів показував старі збережені фінансові підсумки. Їх прибрано
   з коротких карток: актуальні показники відкриваються у повній картці.
4. Помилка списку має явний стан і повторний запит. Помилка RFM не створює
   порожню аналітику; помилка NPS не видається за відсутність відгуків.
5. Перелік unit-тестів поєднано зі збереженням усіх базових 230 файлів:
   разом 238 файлів. Основна команда `test:unit` залишила штатний runner.

## Докази та межі перевірки

- Цільовий прогін: **160 перевірок, 0 помилок**.
- Повний `npm test` і фінальні підсумки збережені у
  `output/final-sanity/npm-test-complete.log`; machine report містить результат
  останнього завершеного прогону. Використані Node 22.23.1 / npm 10.9.8.
  Прогін завершився з кодом 0: 3364 unit-перевірки й 344 My Day-перевірки
  пройшли; штатні перевірки доступу, ownership, синтаксису та додаткові
  набори також пройшли.
- Static UI: **1327 перевірок, 0 помилок** після узгодження очікування
  успадкованого birthday-фільтра.
- Перевірка diff та самодостатності загального patch записана у machine report.
- Browser QA: фактичні `customers.html`, `js/customers-page.js` і CSS,
  синтетичні відповіді API, тестовий bootstrap користувача. Це не справжня
  Express → PostgreSQL перевірка і не live-site QA.
- В браузері пройдено desktop 1440×900 і mobile 390×844: групування,
  пошук → картка → Omni в новій вкладці, кілька діалогів і закритий діалог,
  повернення зі службового інструменту на сторінку 2, фокус і Escape,
  birthday-тег через Enter → preview, зміна тексту → скидання preview,
  явні помилки й повторний пошук, порожній результат, NPS-історія,
  уточнення дітей, усі сім сортувань і поля дат, старі посилання.
- Обмежений синтетичний користувач не бачить RFM, фінансову колонку та
  уточнення дітей. Реальні ролі/auth не змінені; production-акаунти
  у цій перевірці не використовувалися.
- Світлу й темну теми перевірено за screenshots. На перевірених
  viewport немає горизонтального переповнення. Очікувані HTTP 503 створювалися
  тільки локальним стендом; їх відрізняємо від помилок JavaScript.
- PostgreSQL-набори підготовлені, **не виконані**. Локальний Docker daemon
  не відповів на read-only probe протягом 5 секунд. Production DB як
  заміна не використовувалася.
- Публічна live-перевірка стосувалася тільки версії. Змінений розділ ще
  не розгорнутий, тому його production-сумісність не підтверджена.

## Наступний крок

На ізольованій disposable PostgreSQL-базі виконати:

```text
npm run test:integration:omni-links:isolated
npm run test:integration:customer-birthdays:isolated
```

Наявний CI job «Omni browser regression» запускає першу команду та
включає також birthday SQL і HTTP/PostgreSQL-перевірку бізнес-ізоляції.
Окрема друга команда залишається доступною для цільового повторення.
Конфігурація CI не змінюється.

Runner вимагає `TEST_DATABASE_URL` і
`TEST_DATABASE_RESET_CONFIRM=RESET_DISPOSABLE_TEST_DATABASE`; він очищає
саме disposable-базу. Значення URL не зберігати у звітах. Перша команда
включає клієнтські метрики й Omni-зв’язки; друга — birthday SQL.

Після успіху підготувати конкретний реліз: перевірити актуальність live/remote
SHA, виконати окрему версійну підготовку, отримати bounded authorization для
production, пройти CI точного SHA, deploy та спільний live-маршрут. Користувач
прямо дозволив завершити тестування й довести ці зміни до production.
У live QA
використати тільки погоджені тестові записи; без повідомлень або merge.

Не потрібні нові міграції, залежності, ролі, інтеграції чи видалення модулів.
Історичні журнали, оцінки й дані дітей автоматично не переписуються.
