## Знайдене й виправлене

1. **Неповні лічильники підготовки.** API рахував тільки шість завантажених задач. Тепер SQL рахує всі задачі в чинній області видимості, а обмеження стосується лише короткого списку.
2. **Неточний перехід події.** Посилання відкривало день у таймлайні без вибору події. Тепер використовується наявний канонічний огляд `booking-summary.html` з точним ID і бізнес-контекстом. Booking modal, його власник, джерела деталей і protected manifest не змінені.
3. **Часові межі.** День і поточний час API беруться з одного моменту в Europe/Kyiv, із секундами. Подія, яка вже почалася в поточній хвилині, не видається за майбутню. Відкрита вкладка переоцінює найближчу подію й зміну дня.
4. **Старі або неповні рекомендації.** Орієнтир більше не використовує кеш після помилки/відмови доступу, не зависає в loading при відмові всіх джерел і не сприймає порожній JSON як доказ спокійного дня.
5. **Неправильний пріоритет.** Відсутність доступних задач підготовки більше не перекриває особисту задачу чи воронку. Рекомендація про прострочення не веде до довільної першої задачі з майбутнім дедлайном.
6. **Неузгоджені показники після виконання.** Оновлюється також верхня статистика. Запит зміни статусу зберігає бізнес-контекст. Підтверджену сервером задачу не можна повторно виконати з кешованої картки після помилки оновлення. Відповідь попереднього контексту користувача не змінює новий фокус.
7. **Зайві запити при запуску.** Shared setter користувача запускав джерела орієнтира до гідратації налаштувань; при помилці вони запитувалися знову. Передчасне завантаження прибране. У браузері перевірено по одному запиту кожного потрібного віджета, зокрема для повільних відповідей і 403/503.
8. **Мобільна композиція й доступність.** Статистика компактна в один ряд, прибраний зайвий вертикальний простір, виправлений контраст «Налаштувати». На мобільному повний зміст картки читається прокручуванням сторінки. Деталі фокусної задачі — клавіатурне посилання. Перемикачі налаштувань мають назви й видимий фокус, діалог використовує спільний focus trap. Нульові показники ризику нейтральні.

Основні файли DASH-05: `dashboard.html`, `js/dashboard-page.js`, `css/dashboard-widgets.css`, `routes/dashboard.js`; цільові тести, локальний браузерний стенд і сценарій демонстрації. Попередні зміни `config/roles.js` та інших файлів DASH-01—04 збережено; нових змін ролей чи дозволів у DASH-05 немає.

```powershell

npx --yes --package @playwright/cli playwright-cli -s=dash05 run-code --filename tests/browser/dashboard-presentation-browser-qa.js
```

## Неперевірене й наступний крок

- Live-site QA **не виконана**: реліз не погоджений у цій задачі й не здійснювався.
- Не перевірено цей Dashboard→Express→PostgreSQL наскрізно. Перевірки агрегації використовували mock DB; локальний Docker не відповів на read-only перевірку доступності, запит зупинено. Реальну БД не відкривали.
- Фактичний вхід різними ролями, повторювана задача через реальну БД та повне завантаження етапу Leads потребують перевірки на тестовому акаунті після окремого релізу. Серверні правила мутації задач і повторення залишаються канонічними.
- Демонстраційні скріншоти показують явно вибраний набір із п’яти віджетів. Існуючі персональні набори автоматично на нього не замінюються.

Рекомендований наступний крок: локальна репетиція за сценарієм; окремим блоком підготовки релізу узгодити worktree з новим upstream. Після окремого погодження релізу — CI для точного SHA та live QA тільки на тестових записах.
