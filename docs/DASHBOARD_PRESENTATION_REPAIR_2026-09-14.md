## Причини та результат

1. focus_rank=0 потрапляв у список із підписом «у фокусі». API відрізняє обрані задачі від рекомендацій, повертає повні лічильники окремо від preview та актуальний робочий строк. Архівні, завершені й відкладені задачі не стають рекомендаціями.
2. Старий deadline і загальні прострочення підміняли поточну справу. Орієнтир і список використовують спільний вибір кандидатів; строки спираються на канонічну workload/overdue policy.
3. Дії блокувалися лише за парою task/action. Одна задача тепер має спільне блокування виконання, фокуса та відкладання. Успіх показується після відповіді сервера; залежні дані перечитуються.
4. Повторний setter користувача інвалідував усі віджети. Dashboard порівнює зміст контексту; реальна зміна акаунта/сесії перечитує конфігурацію, бізнесу/дозволів — дані. Застарілі відповіді відкидаються.
5. Пропущені бізнес- та visibility-фільтри додано чинними helpers. Глобальні legacy-джерела поза підтримуваним бізнесом повертають недоступність, а не чужі дані.
6. Ціни бронювань називалися доходом/прибутком. UI показує вартість підтверджених бронювань із валютою; сумісне поле profit повертає null.
7. Помилки підмінялися порожніми масивами й нулями. Агрегації зберігають meta.sourceStates, meta.warnings, partial та невідомі значення; UI пропонує повтор.
8. «Завтра» рахувалося як +24 години. Використовується календарний день Europe/Kyiv; виправлено неділю/межі тижня й HR-дати.
9. Контроли, меню та довгі підзадачі знищували пріоритет екрана. «Сьогодні» має компактну статистику, фокус 8/12, подію 4/12, нейтральні поверхні, SVG-іконки й короткі списки.
10. Загальний лічильник воронки відкривав лише гарячий етап, початковий Leads-запит губив attention, а завершені ліди потрапляли у вибірку активних. Переходи зберігають бізнес, фільтр lifecycle=active і точну умову давності контакту; початкове завантаження й наступні сторінки використовують спільні параметри.
11. Два обробники зміни контексту відкидали щойно розпочате завантаження каталогів. Усі інвалідації тепер відбуваються перед запитами; старі відповіді не можуть повернути попередні дані.

## Явний порядок орієнтира

| Порядок | Підстава |
|---|---|
| 1 | Близький робочий строк задачі; прострочена підготовка або початок події сьогодні протягом двох годин |
| 2 | Незавершена домовленість із клієнтом, строк якої настав |
| 3 | Задача, явно обрана користувачем у фокус |
| 4 | Інша актуальна справа або підготовка майбутньої події без термінового ризику |
| 5 | Перегляд накопичених справ зі старим робочим строком |
| 6–7 | Перевірка невідомої підготовки / давності контакту, якщо немає конкретнішої дії |

Давність контакту не є домовленістю. Follow-up береться з чинних незавершених lead_interactions: ліміт WorkQueue застосовується окремо до кожного джерела, тому найраніша домовленість не губиться серед інших сигналів. Час події для порівняння передається додатковим startsAt, отриманим у PostgreSQL через Europe/Kyiv.

## Персоналізація та сумісність

- Нові набори застосовуються лише до початкової конфігурації або після явного preview/підтвердження.
- Збережений набір та порядок не переставляються при оновленні продукту.
- layout.widgetSizes: standard, wide, full; старі side/compact сумісні зі standard.
- layout.mobileOrder зберігається для рекомендованого набору. Старі конфігурації без поля зберігають порядок. Мобільний DOM переставляється разом із візуальним порядком.
- Часткове збереження не переписує невідомі layout-поля та старий boardState. Чинні server revision/CAS і перевірки сесії збережено.
- Переміщення, розмір і приховування доступні у режимі «Налаштувати»; каталог окремо дозволяє вибрати набір.
- Прострочена підготовка: /tasks?source_type=booking&overdue=1. Особисті прострочення: /tasks?dashboardFilter=my-overdue. Умови відбору збігаються з Dashboard-лічильниками.

## Походження доказів

- Node 22 / npm 10: HTTP/SQL-binding, JSDOM та часові тести. Mock pool не є перевіркою production-БД.
- Окрема disposable PostgreSQL 16.15: реальний HTTP → Express → PostgreSQL перевірив два бізнеси, приватність, typed owner, focus_rank=0/1, snooze, майбутній робочий строк, збіг обох overdue-вибірок і канонічне виконання з повторною перевіркою БД. Тест: tests/integration/dashboard-scope-postgres.integration.test.js. Ізольований кластер штатно зупинено; production-БД ця перевірка не змінювала.
- Ізольований браузер на HTML/CSS/JS продукту: п'ять розмірів × дві теми, увесь каталог, меню, редагування, effective 200% viewport. Синтетичні записи не переносяться у CRM.
- Артефакти: output/playwright/dashboard-presentation-repair/.
- Приймання production виконується після exact-SHA CI та штатного deploy. Release/live evidence зберігається окремим санітизованим звітом.

## Обмеження

- Спеціальні overdue-вибірки зберігаються URL; чинний saved-view контракт їх не підтримує.
- Фінанси, склад, контент і права інших ролей не вважаються live-перевіреними лише за наявністю коду.
- Недоступні legacy-джерела позначаються в UI; їхня бізнес-модель не розширюється.
- Відкат: попередній підтверджений production SHA через штатний release helper, без переписування Git-історії.
