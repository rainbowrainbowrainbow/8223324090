# Omni → лід: аудит і план реалізації

Дата: 11.09.2026. Запит: полегшити створення ліда з клієнтського діалогу, додати AI-заповнення редагованої чернетки та використати наявні напрацювання.

## Погоджений план і порядок активації

Оновлено 11.09.2026 після запиту власника перевірити погодження, записати задачі й підготувати короткі активатори та доповнення «вацап треба ще додати до сюди. в таски також додай». **Погоджено план п’яти історій, їхні залежності та виконання на GPT-5.5 з reasoning effort high. Реалізація ще не запускалася.** Поточне доручення стосується підготовки задач; код, commit/push і production у цьому кроці не змінюються. Для нового WhatsApp-обсягу окремо названі необхідна міграція, webhook boundary і межа між випуском коду та активацією акаунта.

| Історія / запуск | Погоджений результат | Передумова | Стан |
|---|---|---|---|
| OMNI-L1 | Спільний перевірений create contract, збереження полів і атомарний lead/link | Актуальна база та ізольоване робоче дерево | Погоджено; не запущено |
| OMNI-L2 | Редагована ручна чернетка біля чату | Реалізація та handoff L1 | Погоджено; не запущено |
| OMNI-L4 / manual | Перевірка й випуск L1+L2 | Реалізація та handoff L2 | Погоджено план; запуск релізу окремим активатором |
| OMNI-L3 | Direct OpenAI preview у тій самій формі | Підтверджений результат першого випуску | Завершено локально; очікує L4/AI |
| OMNI-L4 / AI | Перевірка й випуск AI-заповнення | Реалізація та handoff L3 | Наступний запуск: commit → push → CI → deploy → live QA |
| OMNI-L5 | WhatsApp у спільному Omni inbox, lead create та AI draft | L1–L3; послідовно після другого релізу | Виконано локально в worktree; без commit/push/deploy |
| OMNI-L4 / WhatsApp | Перевірка й випуск коду каналу WhatsApp | Реалізація та handoff L5 | Наступний крок; live-активація залежить від конкретного бізнес-акаунта |

Це **п’ять історій та сім послідовних запусків**: L1 → L2 → L4/manual → L3 → L4/AI → L5 → L4/WhatsApp. L4 використовується перед кожним релізом. WhatsApp — окремий третій випуск; відсутній доступ до його акаунта не блокує перші два. Погоджений UI — редагований drawer біля чату; handoff у повну форму Leads залишається запасним варіантом, а не окремою паралельною реалізацією.

Погоджений обсяг L1 включає застосування чинних Leads guards, бізнес-ізоляції та приховування фінансових даних до Omni create. Погоджений обсяг L3 включає вузький direct OpenAI preview через наявний серверний key boundary і відповідне уточнення provider contract. L1–L4/manual/AI не потребують змін схеми. Для L5 заплановано вузький виняток: міграція, що розширює CHECK дозволених каналів значенням `whatsapp`, і machine-auth boundary тільки його webhook. Активатор L5 прямо називає ці захищені зміни. Розширення ролей, інші міграції, нові залежності, secrets/env, глобальне перемикання OpenRouter, hosting settings та реальні клієнтські мутації не входять у цей пакет.

Надісланий власником активатор L1–L3 або L5 запускає реалізацію і неруйнівні перевірки названої історії. Не просити повторного погодження її вже визначеного обсягу. Активатор L4 окремо містить явне доручення на `commit → push → CI → deploy → live QA`; до його надсилання це план випуску. Для активованого live QA дозволений у тексті активатора обсяг обмежений тестовими обліковими записами та явно синтетичними тестовими записами, без зовнішніх повідомлень і видалення даних. Масовий платний AI-eval не входить у пакет; активатор другого релізу окремо обмежує живу перевірку п’ятьма preview-запитами на синтетичних діалогах. L5 і L4/WhatsApp не дають дозволу прив’язувати/переносити реальний номер, змінювати Meta subscriptions чи надсилати WhatsApp-повідомлення: для цього потрібні конкретний тестовий акаунт, номер, бізнес і погоджений обсяг. За їх відсутності завершити код та перевірки, зафіксувати ACTIVATION_PENDING і конкретний залишок, не заявляти про підключений канал.

Передача роботи між виконавцями:

- План зараз є локальним файлом у початковому workspace. Новий worktree може його не містити: спочатку прочитати `C:/Users/Plotva/OneDrive/Документи/EventGenix/docs/OMNI_CHAT_TO_LEAD_AUDIT_AND_STORIES_2026-09-11.md`, потім зберегти актуальну копію в робочому дереві пакета. Відсутність файла в новій гілці не означає відсутність погодженого плану.
- L1 фіксує повний шлях робочого дерева, branch, базовий SHA та виконані зміни. L2 продовжує саме цей результат, а не незалежний checkout без L1. L3 спирається на підтверджений перший реліз; подальші upstream-зміни враховуються без втрати попередніх доробок.
- L5 спирається на готові L1–L3: WhatsApp додає джерело розмов, а не власні таблиці лідів, форму чи AI-провайдера. Live-активацію та release-ready код обліковувати окремо.
- Кожний запуск зберігає у робочому дереві `docs/OMNI_CHAT_TO_LEAD_PROGRESS_2026-09-11.md`: історія/режим, стан реалізації, повний worktree path, branch/base SHA, перелік змін, commit SHA за наявності, фактичні перевірки, пропуски та наступний запуск. Файл створює перший виконавець; наступні доповнюють його. Посилання на нього обов’язкове у фінальній відповіді.
- L1–L3 можуть бути готові локально до свого релізу; це не позначається як виконане live QA. Для L4 фіксуються окремо CI exact SHA, deployment, `/api/version` і результат live QA. Жоден наступний виконавець не приймає повідомлення «готово» без конкретного handoff.

## Висновок

Будувати Omni або lead intake заново не потрібно. Є історія повідомлень, бізнес-контекст, відповідальні, створення ліда, точні та ймовірні CRM-зв’язки, AI-аналіз і канонічна форма ліда. Проблема — у незручному вході в цей сценарій та розходженні старого Omni assistant із сучасним контрактом Leads.

Рекомендація: **видиме «Створити лід» → редагована «Чернетка ліда» біля чату → необов’язкове «Заповнити з чату AI» → перевірка менеджером → «Створити лід» → точний зв’язок і «Відкрити лід».**

Перший випуск: надійний ручний сценарій. Другий: AI-заповнення цієї самої форми. Третій: канал WhatsApp у цьому ж сценарії. Задачі реалізації — GPT-5.5, reasoning effort high, послідовно; перевірки додаються в кожній задачі.

## Наявний шлях і прогалини

Поточний сценарій: відкрити діалог → AI → автоматичний аналіз → статичний блок «Draft ліда» → «Створити лід». Backend записує лід і його зв’язок із розмовою в одній транзакції. Послідовний повтор повертає існуючий лід, не оновлюючи його полями нової чернетки.

| Проблема | Доказ у поточному коді | Практичний наслідок |
|---|---|---|
| Створення заховане в AI; поля не редагуються | `omni.html:3507–3511`, `3594–3617`, `3886`, `4114–4133` | Менеджеру потрібен AI-analysis навіть для ручного створення; перед записом немає нормального виправлення фактів. |
| Окремий застарілий SQL insert | `services/omniLeadAssistant.js:1704–1794` проти `routes/leads.js:2598–2744` | Немає сучасних `eventPreference`, кількості дорослих, валідації відповідального та належного використання customer/stage contracts. |
| Примітки можуть губитися | `normalizeLeadDraft` зберігає `lead.notes`, але `buildLeadNotes:1673–1696` їх не додає | Наприклад, побажання про динозаврів із тестового fixture не потрапляє як власна примітка. |
| Відповідальний чату не переноситься | Omni зберігає username, Leads очікує перевірений user ID; Omni insert не задає `assigned_to` | Вибрана у шапці Віталіна не означає автоматично відповідальну за створений лід. |
| Одночасне створення не завершується коректним повторним результатом | Пошук існуючого ліда до BEGIN; INSERT без обробки конфлікту; у migration 207 уже є бізнесовий UNIQUE | БД захищає від однакового дубля, але другий менеджер/повтор може отримати 500. Нова таблиця для цього не потрібна. |
| Різні джерела істини для зв’язків | Create перевіряє meta/external ID; context resolver також бачить `conversation.customer_id → customers.lead_id` | UI може показати пов’язаний лід, а create-flow — не врахувати цей зв’язок. Потрібне узгодження його семантики, а не сліпе злиття. |
| Аналізуються перші 120 повідомлень | `getConversationBundle:1515–1521`, виклик із 120 на `:1533` | Нові уточнення дати, гостей чи формату в довгій переписці залишаються за межами аналізу. |
| Відкриття AI має запис у БД | `analyzeConversationLead:1539`, `recordConversationLeadAssistantAnalysis` | Навіть preview оновлює summary/meta/updated_at розмови. Новий preview має бути явно відокремлений від збереження ліда. |
| Евристики можуть підставити непідтверджений факт | `extractFallbackLead:692–700` змішує inbound/outbound, `normalizeAnalysis:1037–1038` відновлює fallback після AI null | Приклад менеджера або старий телефон/дата можуть стати полем клієнта. Невідоме значення не повинно маскуватися під визначене. |
| Рекомендація може стати замовленням | `buildLeadInsertDraft:1725` бере програму з першого рекомендованого матеріалу; бюджет пишеться в potential_value | Програму потрібно підтверджувати, а значення бюджету узгодити з канонічною семантикою поля. |
| Слабкий контракт AI і підтвердження | Schema лише текстом у prompt; приймається цілий `body.analysis`; немає field→message evidence/snapshot | JSON-подібний результат не гарантує правильних фактів; перед записом потрібна серверна валідація дозволених полів і джерела чернетки. |
| Розходження доступу/фінансового приховування | Omni перевіряє Omni+business; Leads має свої guards та `shapeRevenueResponse`; Omni повертає повний row | Потрібно повторно використати чинні правила операції з лідом, не розширюючи ролі й не повертаючи зайві фінансові дані. |
| Неповний захист стану під час create | Analyze уже має захист від запізнілого результату, create-handler — неповний; при перемиканні analysis скидається | Успішна дія в чаті A не має змінити вигляд чату B; AI не повинен затерти ручні правки. |

Симптоми для bug report: ліда важко створити; дані неможливо виправити перед записом; сучасні поля/відповідальний не переносяться. Очікування: коротка редагована форма, правильні source links та один запис після явного підтвердження. Статичний шлях відтворення: AI → Draft → create; для інших дефектів — сценарії в QA-матриці нижче. Імовірна спільна причина: inbox оновлювався, а старий assistant/save mapping розвивався окремо від Leads.

## Що використати повторно

- `conversations`, `conversation_messages`, існуючі scope/identity/provider adapters. Для базового «чат → лід» нові webhook не потрібні; доданий окремо WhatsApp потребує власного адаптера й webhook у L5.
- `routes/omnichannel.js` та `services/omniLeadAssistant.js`: наявні маршрути, provenance/source metadata, транзакційний зв’язок, сумісність старого клієнта.
- Канонічний Leads contract: `routes/leads.js`, `leads.html`, `js/leads-page.js`, чинні нормалізатори event preferences/celebrants і правила customer/stage. Виділити тільки необхідні спільні функції; не переписувати весь великий router.
- `services/omni-hub.js:647` і UI context: точний зв’язок окремо від ймовірного збігу; deep links у лід і назад зі збереженням business context.
- Наявний UNIQUE `(business_context, source_channel, external_id)`. Захистити транзакцію row lock/recheck або коректною conflict handling зі scoped перечитуванням.
- Локальні patterns чернеток composer за `businessContext:conversationId`, epoch guards, focus trap та mobile back. Не додавати тексти розмов/чернеток у незахищене довготривале browser storage.
- `js/crm-create-handoff.js` і `js/leads-page.js:1311–1382`, `4726–4748` як альтернатива: вже є відкриття канонічної create-форми та повернення `lead.created`; prefill/safe conversation linking потрібно доробити.

## Варіанти реалізації

| Варіант | Перевага | Недолік | Рішення |
|---|---|---|---|
| Редагований drawer біля чату, спільний серверний контракт Leads | Переписка перед очима; manual і AI працюють в одній формі | Потрібне узгодження полів і state із Leads | **Рекомендовано** для щоденної роботи менеджерів. |
| Handoff до вже наявної форми у «Лідах» | Менше нового UI; повторне використання повної форми | Перехід відводить від переписки; потрібні повернення й атомарне linking | Запасний варіант, якщо головний пріоритет — мінімальний обсяг першого релізу. |

Повний rewrite Omni не дає потрібної продуктової вигоди. Scoring, каталоги, редактор сценаріїв, автозадачі та чернетки відповідей не потрібно включати до нового головного сценарію. Їх не видаляти мовчки; зберегти сумісними у другорядному assistant UI.

## Пропонований MVP-контракт

1. Ручна чернетка відкривається без виклику AI. Підставляються відоме ім’я/контакт і канал; видима назва акаунта не видається за підтверджене ім’я людини. Для мінімального збереження використовуються чинні вимоги Leads, а не весь старий список AI-required fields.
2. Основні поля: ім’я, доступний контакт, джерело, дата, кількість дітей/дорослих, вік/іменинники, формат/побажання, примітки, відповідальний — лише через поля сучасного Leads contract. Окремого структурованого часу в цьому контракті немає: побажання щодо часу зберігати в примітках без нової схеми. Рідше потрібні поля розкриваються додатково. Бюджет показується тільки за чинними правами й з узгодженою семантикою. Не вводити паралельну схему «AI-ліда».
3. Канал, business context та conversation identity задає сервер. Відповідальний пропонується з поточного чату через перевірене username→user ID; якщо відповідність недоступна — явний незаповнений вибір, без довільної підстановки.
4. Preview нічого не створює в leads/customers/tasks і не змінює status/assignee/summary чату. Скасування не залишає бізнесових записів. Постійне зберігання чернеток, спільні чернетки між менеджерами та відновлення після reload — поза першим MVP.
5. Підтвердження: вузький allowlist payload, серверна валідація, дозволи чинного Leads-сценарію, атомарні lead+link, idempotent повтор. Стара API-відповідь зберігається сумісною; нова не повертає зайвих даних.
6. Якщо чат уже явно пов’язаний із лідом — «Відкрити лід» замість другого створення. Старий `customers.lead_id` показати як контекст клієнта: він не завжди доводить, що поточна розмова стосується тієї самої події. Ймовірні збіги — лише пропозиції менеджеру.
7. Сьогодні `external_id = omni_conv_<id>` означає один основний лід на розмову. Повторне нове свято того самого клієнта — важливий наступний сценарій; не обходити UNIQUE випадковим суфіксом. У цьому MVP залишити явний шлях до канонічного створення нової угоди клієнта без мовчазної переприв’язки чату. Повноцінна історія кількох звернень у одному чаті потребує окремого продуктового рішення про зв’язки.
8. Створення ліда не закриває чат, не змінює етап існуючого ліда, не створює бронювання/платіж/розсилку й не надсилає повідомлення. Правила матеріалізації customer залишаються чинними для відповідного етапу; не створювати картку клієнта лише через preview.

## OpenAI: поточний стан і ціль

**Поточний Omni assistant використовує OpenRouter**, а не пряме OpenAI-підключення: `callUnifiedChatCompletion` у `services/omniLeadAssistant.js:1447`, `services/ai-config.js`, [provider contract][provider-contract]. Наявність `OPENAI_API_KEY` сама по собі цей старий шлях не активує. Конфігурація production-ключів у цьому аудиті не перевірялася.

Для запитаної нової кнопки рекомендований окремий вузький direct OpenAI preview у наявному Omni/Leads контурі. Це слід явно зафіксувати у provider contract як рішення для цієї функції; не перемикати глобально Chat/Guardian/інші OpenRouter можливості.

У проєкті вже є direct Responses API patterns у `services/myDayTaskOpenAIClient.js` та menu draft flow. Корисні: `json_schema`, `store:false`, timeout/AbortController, контрольований missing-key/error, заборона реального OpenAI у звичайних тестах. My Day client жорстко прив’язаний до власної моделі та rollout-правил; імпортувати його цілком в Omni не слід. Достатньо невеликого Omni adapter або мінімального спільного transport helper, якщо це справді зменшить дублювання; новий SDK не потрібен.

AI preview має:

- читати серверний зріз **конкретної розмови й бізнесу** зі стабільним порядком повідомлень, ролями авторів і часом; включати актуальні уточнення та явно повідомляти про обмеження історії;
- для MVP використовувати обмежений актуальний текстовий контекст із можливістю додати вибрані попередні повідомлення; порожні файли/voice без транскрипту не трактувати як прочитаний зміст;
- повертати strict schema: поля, невідоме як null, список пропусків/конфліктів та прив’язку кожного запропонованого факту до message ID; фактичність перевіряється додатково, сама JSON Schema її не гарантує;
- розрізняти запит/підтвердження клієнта, пропозицію менеджера і цитований старий текст; «можемо 15:00» не означає погоджений час; нове явне уточнення переважає попереднє;
- враховувати часову зону Києва й timestamp повідомлення для відносних дат; неоднозначний рік/дата залишається для перевірки менеджером;
- повертати conversation ID, business context і token/digest зрізу, який враховує нові повідомлення та редакції; client і server перевіряють належність чернетки, а при застаріванні пропонують повторний аналіз або явний перегляд;
- застосовувати значення тільки до незмінених менеджером полів; для заміни ручної правки потрібен явний вибір, без автоматичного перезапису;
- мати timeout, ліміт довжини/частоти, loading/retry/cancel і зрозумілий fallback до ручної форми; не видавати regex-відновлення за успішне AI-заповнення;
- не мати send/create/update tools; текст клієнта розглядати як дані, а не інструкцію AI. У logs/fixtures не зберігати сире листування, телефони чи ключі; технічні метрики — без змісту.

Модель виконавця задач і модель всередині CRM — різні рішення. **GPT-5.5/high — для реалізації цього плану.** API-модель preview вибрати з уже доступних direct OpenAI моделей після короткої оцінки якості/часу/вартості на синтетичних діалогах. Не призначати GPT-5.5/high кожному натисканню за замовчуванням. OpenAI документує high для GPT-5.5; Structured Outputs забезпечує форму відповіді, але потребує обробки refusals і помилок та не усуває потреби перевіряти факти. Джерела: [GPT-5.5][openai-55], [Structured Outputs][structured-outputs].

## WhatsApp: доданий обсяг OMNI-L5

На перевіреному production SHA WhatsApp існує тільки як контактне поле у lead/booking payloads (`routes/leads.js:1301–1339`, `services/leadBookingLink.js`). **Підключеного Omni-адаптера немає.** `services/omni-accounts.js`, `services/omni-hub.js:39` та normalizer не реєструють цей канал. `db/migrations/052_omnichannel.sql:7` обмежує `conversations.channel` CHECK-списком без `whatsapp`; для нового каналу потрібна окрема безпечна міграція, а не редагування історичної 052.

Робоче припущення для плану — **офіційний WhatsApp Business Platform / Cloud API**. Виконавець перевіряє придатність наявного номера/акаунта; не обіцяє підключення особистого WhatsApp скануванням QR і не мігрує активний номер самостійно. Особистий акаунт через неофіційний міст — інший scope. Meta API використовує WABA та business phone-number ID; для шаблонної відправки потрібен уже створений шаблон. Джерела: [Meta: phone number ID][wa-phone], [Meta: template messages][wa-templates]. Доступ до загальної developers.facebook.com документації під час підготовки повернув 429; звірено доступні первинні сторінки офіційної колекції Meta, а повний чинний messaging contract виконавець перевіряє перед реалізацією.

MVP: один WhatsApp Business номер на бізнес-контекст, особисті текстові діалоги клієнтів, ручна відповідь у дозволеному provider-ом вікні, receipts, пошук/фільтр/відповідальний/стан, та повний спільний шлях «WhatsApp чат → ручна або AI-чернетка → лід». Поза дозволеним вікном довільна відправка блокується з поясненням про approved template; повний редактор шаблонів і кампанії не входять у MVP. Вкладення й непідтримувані типи мають чесне відображення, без удаваної відправки чи AI-читання вмісту; реалізація media capabilities може використати наявний storage тільки в окремо визначеному обсязі.

Ідентичність повідомлення/розмови враховує business context, належний WABA/phone-number ID та provider contact ID. Повторна доставка webhook не створює дубль, а receipt не стає новим клієнтським повідомленням. Наявний `/webhook/meta` жорстко орієнтований на Facebook/Instagram: WhatsApp не можна мовчки направити в його Facebook fallback. Потрібні окремий маршрут, raw-body capture, перевірка підпису й явне зіставлення акаунта з бізнесом до будь-якого запису.

Готовність коду та активація сервісу — окремі результати. Без доступного WABA/номера, секретів через затверджений server-side механізм та дозволу на subscriptions/тестового адресата код перевіряється fixtures і disposable PostgreSQL; UI правдиво показує «Не підключено»/«Потрібне налаштування». Чинний номер, його історію й використання у мобільному застосунку не змінювати без окремого рішення власника.

## П’ять історій для GPT-5.5 / high

Нижче — погоджені execution cards. Їх запускають короткими активаторами наприкінці документа; стани та межі наведені в реєстрі вище. Перед роботою виконавець звіряє актуальний live SHA, handoff попередньої історії та правила репозиторію. За основу бере цей документ і поточний код, не застарілий dirty checkout. Не створює нову архітектуру або мікрозадачі без потреби.

## Мінімальна QA-матриця

| Сценарій | Очікуваний результат |
|---|---|
| Новий чат; AI не налаштований | Ручна форма доступна; коректний лід після Save. |
| Cancel, preview без Save | Нуль нових lead/customer/task; статус/summary/assignee чату незмінні. |
| Notes, діти/дорослі, eventPreference, owner | Дані після збереження відповідають підтвердженій формі та канонічному Leads contract. |
| Double click, два менеджери, retry після timeout | Один основний лід, той самий ID; контрольований повтор без 500. |
| Збій linking після INSERT | Повний rollback транзакції. |
| Explicit linked lead / historical customer lead / suggested match | Відмінні зрозумілі стани; немає сліпого merge або перезапису. |
| PARK/DAR, чужий conversation/customer/owner | Чинні guards; відсутність витоку даних; правильний business у переходах. |
| Обмежений доступ до Leads/доходів | Та сама дозволена поведінка й shape відповіді, що в канонічному сценарії. |
| >120 повідомлень із пізнім уточненням | Актуальні факти потрапляють у зріз; обмеження історії видиме. |
| Manager offer, forwarded quote, суперечність дат, missing phone | Непідтверджене не стає фактом; потрібні поля позначені для перевірки. |
| AI null, malformed response, refusal, timeout, 429 | Жодного прихованого fallback-факту; ручна форма та її правки збережені. |
| Перемикання чату/бізнесу, редакція повідомлення, ручні правки під час AI | Snapshot/epoch/dirty-field guards; чужі й застарілі результати не застосовуються мовчки. |
| Prompt injection у повідомленні | Текст залишається даними; AI не виконує команд і не викликає зовнішніх дій. |
| Існуючі status/assignee/close/read/delivery + Leads create | Поведінка збережена. |
| Keyboard, dark mode, 390px, фізичний телефон | Доступна форма й кнопки; фактично перевірені пристрої зазначені. |
| WhatsApp без акаунта, wrong WABA/phone-number/business, forged signature | Правдивий disconnected; сторонні події відхилені до запису. |
| WhatsApp inbound retries, receipts без messages, send timeout | Один вхідний запис; receipt не створює діалог; unknown не провокує повторну відправку. |
| WhatsApp текст → ручна/AI-чернетка → лід | Спільний контракт L1–L3, правильні source/owner/context/link, без окремого pipeline. |
| WhatsApp messaging window, непідтримуваний тип | Неможлива відправка заблокована з поясненням; непідтримуваний вміст не вдає прочитаний AI. |
