# Omni: аудит працездатності та список доробок

Дата: 10 вересня 2026. Перевірена production-версія: **0.81.88**, SHA `aa7865f6075524076a117621b95b352c7c5c91eb`.

## Висновок

Omni вже приймає приватні текстові повідомлення Telegram, але ще не є завершеним багатоканальним робочим inbox. Є помилки інтерфейсу та історії, проблеми надійності обробки подій, а також окремі помилки доступу й сумісності провайдерів. Підключення Viber/SMS/Meta саме по собі їх не усуне.

Під тестовим входом production повернув 2 Telegram-діалоги. Клік «TG» і клік «Всі» обидва дали HTTP 200, 2 розмови та дозволили відкрити діалог. Заявлений постійний збій TG у цьому сценарії **не відтворився**. Водночас у коді підтверджені гонки запитів при швидкому перемиканні та неузгоджений стан чату після фільтрації; це окремі причини нестабільної поведінки, а не доведення причини саме користувацького випадку.

Автовідповіді вимкнені в обох доступних діалогах. Нові повідомлення від імені менеджера під час аудиту не надсилалися. Реальні клієнтські записи, секрети, webhook-конфігурації та налаштування Railway не змінювалися.

## Що фактично перевірено

- Live браузер: «Всі», Telegram, Viber, SMS, Facebook, Instagram; відкриття Telegram-діалогів; пошук/скидання; вкладки Inbox/Канали/Стан; відкриття/закриття 5 форм підключення; кнопки сповіщення про оновлення; ширина 1440 і 390 px.
- Live API лише читання: health, version, канали, список розмов і прапорці AI. Стани: Telegram connected/sendCapable/receiveCapable; інші провайдери disconnected. Health `ok`, БД `connected`.
- Код: frontend, routes, hub, normalizer, усі 5 адаптерів, SMS-fly/TurboSMS, пов'язані тести й офіційні контракти провайдерів.
- Синтетичні відтворення без зовнішніх відправок: Meta echo/службова подія, SMS ACCEPTD, TurboSMS callback, Viber великі message_token, Telegram group ID, AI object/context/duplicate, WebSocket recipient filtering.
- Браузер блокує production POST/PATCH/PUT/DELETE; виняток — вхід тестового користувача. Мутаційні сценарії перевіряються тільки із локальними HTTP fixtures у пам'яті.

Неперевірено: фактична доставка нової ручної відповіді Telegram, реальні Viber/SMS/Meta credentials/permissions/subscriptions, платна SMS, зовнішні receipts, усі ролі менеджерів. Це обмеження доказів, а не твердження про успіх або відмову доставки.

## Пакет виправлень після дозволу власника

**Код реалізовано локально; випуск у production ще не виконувався.** На запит «працюй над виправленням всіх проблем» виконано погоджений блок `OMNI-INBOX-HARDENING`, зокрема зміни перевірки доступу Omni та webhook-контрактів. Автоматичну відповідь зовнішньому клієнту через внутрішнього AI-помічника видалено з ingress-шляху. AI-панель лишається інструментом менеджера з явною дією.

Поки тривав аудит, production оновився до **0.81.89**, SHA `a493fe33be17d5bdcb5ebd6e32b515e3148bbb22`. Пакет перенесено на цей SHA без конфліктів у `.worktrees/omni-inbox-ready`. Раніша `.worktrees/omni-full-audit` зберігає історичні докази на базі 0.81.88. Зміни каси v0.81.89 збережено; вони не входять у diff Omni.

Production impact: yes — після випуску зміняться поведінка inbox, перевірки його API, підписів і квитанцій. Нових production-міграцій, залежностей, змін секретів, змін Railway та реальних відправок немає.

### Змінені області

- `omni.html`, `css/omni-workspace.css`, `js/ws.js` — інтерфейс, стан, доступність і оновлення.
- `routes/omnichannel.js`, `services/omni-hub.js` — API, scope, збереження, повтори, статуси доставки.
- `services/omni-inbox.js` — прочитане, менеджери, захищене завантаження Telegram-вкладень, Meta receipts.
- `server.js`, `services/omni-webhook-payload.js` — raw-body parser тільки для Omni. Загальний JSON parser CRM і Hermes-ліміт збережені.
- `services/omni-accounts.js`, `services/omni-normalizer.js`, адаптери Telegram/Viber/SMS/Facebook/Instagram — контракти та правдиві стани.
- `package.json` і тести Omni, case-link та business-context — regression gate. Залежності й lockfile не змінені.

### Перевірки

- Готова база: Node **22.23.1**, npm **10.9.8**, version **0.81.89**.
- PostgreSQL **16**: окремий loopback-кластер на порту 55439; тести виконали наявні Omni-міграції виключно в нових одноразових БД. Підтверджено 20 одночасних створень → 1 розмова, 20 inbound retries → 1 повідомлення, 20 send retries → 1 виклик тестового провайдера; старіша редакція не перезаписує новішу; mark-read зберігає 10 конкурентних нових входів; квитанції PARK/DAR із однаковим provider ID ізольовані; Meta read, пошук і менеджери працюють. Тест пройшов; тестовий кластер зупинений. Чинний WSL PostgreSQL на 5432 і production БД не змінювалися.
- Chrome, тільки синтетичні Omni API: 105 діалогів/105 повідомлень, чернетки A/B, запізніла історія, send A→B, ID відправки, failed close, призначення менеджера, статуси/«мої»/скидання, feedback каналів, 1440/390 px і досяжність composer — успіх. Реальних записів і відправок **0**.
- Окремий frontend suite після останніх змін — **21/21**, включно зі збереженням сесії після 403 та фіксацією бізнесу/адресата під час асинхронної підготовки відправки.
- Остаточний `npm test` на базі v0.81.89 — **exit 0**: unit **2600/2600**, route smoke **334/334**, UI **1312/1312**; runtime/version/access/auth-boundary/static/CSS/API/storage/service-worker/scheduler/DB-startup/timeline/migrations/syntax checks — успіх. Ранні прогони знайшли й допомогли усунути несумісний marker JSON parser та дві застарілі перевірки буквального запису вже зафіксованого frontend-контексту. PostgreSQL-тест окремо виявив і перевірив виправлення типізації Meta receipt SQL.

Докази готового пакета: `output/omni-final-npm-test.txt`, `output/omni-postgres-tests.txt`, `output/omni-browser-qa.json`, `output/playwright/fixture-omni-1440.png`, `output/playwright/fixture-omni-mobile-composer.png`. Історичні sanitized live-докази залишилися в `.worktrees/omni-full-audit/output/`.

Повтор PostgreSQL-перевірки: створити окрему локальну БД `omni_fixture_test`, передати її URL лише через process-local `OMNI_TEST_DATABASE_URL` і виконати `npm run test:integration:omni`. Потрібний локальний користувач з CREATEDB; тест створює нову БД з випадковим ім’ям і не використовує `DATABASE_URL`.

### Що ще потрібно для повного запуску

1. Погоджений випуск коду, exact-SHA CI і live QA; див. `docs/OMNI_RELEASE_PLAN_2026-09-10.md`.
2. Один погоджений обмін через тестовий Telegram-діалог. Справжніх клієнтів під час цієї роботи не повідомляли.
3. Облікові записи й права Viber/SMS/Meta, налаштовані provider callbacks та контрольовані canary; платна SMS потребує окремого дозволу.
4. Вихідні файли/медіа, comments/postbacks і за потреби окремий Instagram Login adapter. Їх не маскує статус «підключено».
5. Коротка перевірка на фізичному телефоні з відкритою клавіатурою.

Залишкове обмеження доставки: якщо провайдер прийняв повідомлення, а БД після цього недоступна, історія може тимчасово лишатися з невідомим результатом. UI показує невизначеність; автоматична повторна відправка не виконується. Потрібне звірення з провайдером, а не новий платний/клієнтський запит навмання.

## Рекомендована послідовність — 5 робочих блоків

1. **Закрити A1–A4:** доступ, квитанції, сесія і зовнішній AI. Це першочерговий захищений пакет.
2. **Закінчити Telegram inbox:** локальні C1–C5, B1–B5, одне контрольоване тестове спілкування. Не включати AI.
3. **Довести повсякденний цикл:** вкладення, unread, статуси, відповідальний, мобільна робота.
4. **Підготувати й увімкнути провайдери по одному:** Viber, обраний SMS, потім Meta DM; кожен має окремий контрактний та живий тест.
5. **Фінальний наскрізний прохід:** менеджерська роль, PARK/DAR, повтор webhook, timeout/unknown send, 101+ історія, перепідключення і зрозумілі помилки. Жодного автоматичного повтору невідомої платної відправки.
